## 왜 아침 2회 + 오후 2회인가

기본 목표는 **개발자가 출근해서 볼 때 채널에 있는 것**이다. 그래서 아침 08:00·10:00이 주 전달이고,
저녁~새벽 게시분은 다음날 08:00에 잡힌다.

오후 14:00·16:00은 **미러 지연을 흡수하기 위한 것**이다(아래 참고). 오전 실행 시점에 미러가
아직 원본을 못 따라잡았으면 그날 오후에 잡는다.

실행 간격: 08→10 (2h) / 10→14 (4h) / 14→16 (2h) / 16→다음날 08 (16h).
최대 공백 16시간에 미러 지연을 더해도 48시간 판정 창 안에 들어온다.

## ⚠️ 커버리지는 두 단계다 (실패 사례)

`v1.30096.1`을 실제로 놓친 적이 있다. routine은 원본이 아니라 **미러**를 읽으므로
조건이 하나가 아니라 둘이다:

```
게시 → 미러가 받아야 함 → 그 다음에 routine이 돌아야 함
```

2026-08-14 실패 타임라인 (KST):

| 시각 | 사건 |
|---|---|
| 08:42 | Actions 실행 → 미러 갱신 (아직 구버전) |
| 09:12 | **원본에 v1.30096.1 게시** |
| — | Actions가 09:42·10:42 회차를 건너뜀 |
| 10:00 | routine 실행 → 08:42 시점 미러를 읽음 → "새 릴리스 없음" (판단 자체는 정상) |
| 11:04 | 미러가 뒤늦게 갱신 — 그날 routine은 이미 종료 |

이전 문서에 적혀 있던 "실측 15건 전수 15/15 커버"는 **`게시 → routine 실행` 간격만 계산하고
중간의 미러 지연을 빼먹은 수치**였다. 실제 조건은 위와 같이 2단계다.

대응: routine을 오후까지 4회로 늘리고, 미러 주기를 15분으로 줄였다.
## 실행 주기를 바꿀 때

`0 23,0,1 * * *`의 시각(UTC)을 고치되, **최대 실행 간격이 48시간을 넘지 않도록** 유지할 것.
넘기면 프롬프트 2단계의 판정 창을 벗어나 릴리스를 조용히 놓친다.
routine cron의 최소 간격은 1시간이다.

또한 **미러 주기보다 촘촘하게 잡아도 의미가 없다.** routine이 보는 것은 미러이므로,
미러가 갱신되지 않았으면 몇 번을 돌려도 같은 데이터를 읽는다.
